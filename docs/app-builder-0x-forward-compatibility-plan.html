0.x Forward Compatibility

A plan for allowing already-installed 0.x launchers to resolve and run a 1.x app-builder ref, while keeping the explicit bundled 0.x bridge isolated and leaving unrelated Python environments untouched.

Investigated 6 August 2026 · implementation target: app-builder 1.x

Decision

The committed compatibility package will be named __app_builder_0x_version_bridge__. The root requirements.txt becomes a small shipper into that directory. Installing those requirements plants a relocation-safe bridge in the legacy version venv; the bridge activates only when that venv is launched from a proven 0.x version-cache layout.

The bridge first makes the requested 1.x ref runnable. Promotion of the outer 0.x installation is a separate, deferred operation performed by the real 1.x installer after the old process exits.

Rename Applied Now

The generated bundled bridge has been renamed from __app_builder_0.x__ to __app_builder_0x__. The new name is used by the dogfood config, generator default, runtime dispatcher, tests, documentation, and ignore rule.

Why it remains ignored

__app_builder_0x__ is generated release input, like bin/python. The build script assembles the pinned v0.20.0 CLI and dependencies; app_builder.yaml includes that output in the installer.

What it still does

app-builder 0.x <args> dispatches to __app_builder_0x__\app-builder.exe. This explicit compatibility command is unchanged apart from the directory spelling.

What The Legacy Versioner Actually Does

  1. Clones the requested app-builder ref.
  2. Creates a temporary tree containing repo, venv, app-builder.cmd, and run.log.
  3. Runs the new checkout's requirements.txt with the temporary venv's Python.
  4. Copies the completed tree to versions\<requested-ref>.
  5. Runs either repo\app_builder\main.py or python -m app_builder, depending on the installed 0.x launcher generation.

The 3sl ./libpostal line cannot be copied literally

The 3sl installation runs pip from its repository root. The legacy app-builder versioner does not change into the cloned app-builder checkout before invoking pip. A literal ./__app_builder_0x_version_bridge__ would therefore resolve against the user's application directory and fail.

The location-safe form is a nested requirements file. Pip resolves a nested -r path and its --find-links path relative to the requirements file that contains them. This behavior was verified locally with pip 26.1 and a built wheel.

    app-builder.exe          # explicit `app-builder 0.x` runtime
    ...

The root shipper contains only:

-r __app_builder_0x_version_bridge__/requirements.txt

The nested file owns the normal 1.x dependencies and selects the vendored bridge wheel:

--find-links wheelhouse
app-builder-0x-version-bridge==<bridge-version>
click==8.*
poetry==2.*
pyyaml==6.*

The wheel is rebuilt and verified by the release pipeline whenever bridge source changes. Both source and wheel are committed because an already-shipped 0.x versioner only sees files present in the requested Git ref.

Activation Contract

The wheel installs a one-line .pth activator. Python evaluates it when the newly created version venv starts. The activator must return immediately unless every structural proof below succeeds:

  • Windows is the current platform.
  • sys.executable is exactly under <candidate>\venv\Scripts\python.exe.
  • The candidate contains repo, run.log, and the legacy-generated app-builder.cmd.
  • The candidate's parent is named versions; this deliberately excludes pip's temporary assembly tree.
  • The sibling repository contains the expected 1.x pyproject.toml, app_builder, app_builder_meta, and bridge metadata.
  • Every resolved path remains below the candidate version directory before it is used.

Outside that exact layout the package is inert: no files are copied, no downloads start, no registry keys change, and no process is launched. Installing it in an ordinary venv is therefore harmless.

What activation does

  1. Adds the sibling repo directory to sys.path for this process only.
  2. Reads the requested ref from the version-cache directory name and reads the application version from the checked-out pyproject.toml.
  3. Writes an idempotent bridge receipt containing the ref, app-builder version, bridge version, and source-tree fingerprint.
  4. Optionally schedules outer-install promotion when, and only when, the ref maps to a verifiable published 1.x release.

Both Historical Dispatch Modes Must Work

Installed launcherHow it invokes the requested refCompatibility treatment
v0.17 through v0.19.1 Runs repo\app_builder\main.py directly. Make the 1.x main.py a supported direct-entry trampoline as well as an importable module. The activator has already exposed dependencies and records the context.
v0.20.0 Uses python -m app_builder for refs newer than v0.19.0. The activator inserts the checked-out repo at the front of sys.path, so the module is resolved from the requested ref.
Current 1.x explicit bridge app-builder 0.x <args> runs the bundled v0.20.0 launcher. No behavioral change. It merely uses the renamed __app_builder_0x__ directory.

The implementation must use capability tests where it controls dispatch. The historical v0.20.0 comparison against 0.19.0 is not copied: v0.19.1 still lacks app_builder\__main__.py, so file capability is more accurate than a version inequality.

Deferred Promotion To The 1.x Installation

Running a 1.x ref from the old cache and replacing the outer app-builder installation are separate transactions. The first must work even when promotion is unavailable.

1. Resolve a release, without guessing Promotion is allowed only for an exact semantic version with a matching official GitHub release. Branch names and arbitrary commit refs remain cache-only executions.
2. Download and verify The bridge downloads the installer and published checksum metadata over HTTPS into a random directory under %TEMP%\app-builder-downloads. SHA-256 verification is mandatory before execution.
3. Leave the current command alone A detached helper receives the current and ancestor process IDs, verified installer path, log path, and intended version. It waits until the old launcher and bundled Python have exited.
4. Let the real installer own installation semantics The helper runs the verified installer with --yes --no-wait. It does not reproduce PATH, shortcuts, Installed Apps registration, legacy replacement, or uninstall behavior; the tested 1.x installer performs all of those actions.
5. Retain failure evidence, clean success Success removes downloaded temporary files. Failure retains a bounded log and installer path and prints their location on the next bridge run.

No elevation is requested. The target remains the normal per-user %LOCALAPPDATA%\app-builder installation.

Safety And Idempotency

  • The activator performs no persistent action while pip is building the wheel or while the legacy versioner is still assembling its temporary tree.
  • A receipt and process-safe lock prevent duplicate downloads or concurrent promotion attempts for the same release.
  • A successful outer installation at the same or newer version makes promotion a no-op.
  • A failed download or checksum mismatch leaves the existing 0.x installation untouched and does not block version-cache execution.
  • The helper never deletes an unrecognized directory and never writes outside its version cache, bounded log location, or random download directory.
  • The bridge wheel has no generic startup behavior outside a fully recognized legacy cache.

Implementation Sequence

  1. Finish and merge the directory rename. Rebuild the dogfood bridge and prove app-builder 0.x --help uses __app_builder_0x__.
  2. Create the committed bridge package. Add context recognition, the .pth activator, receipts, and strict no-op behavior.
  3. Make both entry styles valid. Support direct execution of 1.x app_builder\main.py and module execution without duplicating CLI behavior.
  4. Turn root requirements into the shipper. Generate the bridge wheel, place it in the local wheelhouse, and make the nested requirements file own 1.x dependencies.
  5. Prove cache-only forward dispatch. Test real historical launcher code before adding any outer-install mutation.
  6. Add verified deferred promotion. Reuse the released 1.x installer and keep this feature independently disableable until its Windows matrix is green.
  7. Document the user-visible contract. Explain that a 0.x installation can run a configured 1.x ref and may promote itself after the command completes; keep package-layout details out of normal user help.

Boundaries

This feature does not make 1.x read application.yaml, does not silently reinterpret a legacy project as 1.x, and does not route normal 1.x commands through legacy code. It only lets an already-installed 0.x version manager materialize and execute an explicitly requested 1.x app-builder ref, then optionally replace its own outer installation through the real 1.x installer.
