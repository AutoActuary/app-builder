Overview

app-builder packages Windows-first applications from app_builder.yaml. It can prepare Python runtimes, run build steps, assemble payload files, create installers, create uninstallers, make Start Menu shortcuts, and publish artifacts to GitHub Releases.

The 1.x line is intentionally Python-focused. Features from old bin/... toolchains are retired except for Python. Non-Python tools still fit naturally through explicit build hooks.

Install app-builder

  1. Download the latest app-builder-<version>-installer.exe from GitHub Releases.
  2. Run the installer. It installs app-builder for the current Windows user and adds the installation directory to the front of the user PATH.
  3. Open a new terminal and verify the installation:
app-builder --version
app-builder --help

Run a newer installer to upgrade an existing app-builder installation. To remove it, open Windows Settings > Apps > Installed apps, select app-builder, and choose Uninstall. The uninstaller also removes app-builder from the user PATH.

Source development

Contributors working on app-builder itself can install the checkout as an editable Python package. This is a development setup, not the normal user installation. 

python -m pip install -e .

Quick Start

Start inside a git repository:

app-builder init

Edit app_builder.yaml. For a Python application, declare dependencies in pyproject.toml and run app-builder lock before the first build. For an application that does not ship Python, set both python_bundled and python_venv to null.

Then build local release files:

app-builder release --version 0.1.0

Build and publish the configured release files to GitHub Releases:

app-builder release-gh --version 0.1.0 --draft

Without --version, app-builder uses git describe --tags --always --dirty. If git cannot provide a version, it uses 0.0.0-dev.

1. Your Project

Your source files, dependencies, icon, and app_builder.yaml. The config tells app-builder what belongs in the application and how it should be installed.

2. The Release Files

app-builder release turns the project into distributable files under installer.dist, which defaults to dist. These include the installer, payload, manifest, checksums, release notes, and any additional configured assets.

3. The Installed Application

The generated installer runs on the user's computer. It installs or upgrades the application, creates shortcuts, registers uninstall support, and carries everything the application needs to run.

4. Publishing Is Optional

app-builder release-gh publishes the selected release files to GitHub. It does not change how the application is built or installed.

Configuration

app_builder.yaml is the contract for a project. The loader is strict: unknown keys are rejected, legacy application.yaml shapes are rejected, and hook commands must be argv lists. The complete shape below is generated from the same schema metadata as app-builder init.

Start from the complete template when you are unsure. It shows every supported field, its default when omitted, and the short help text attached to that config option.

Command Values

Hook fields are list[list[string]]. Each command is an argv list. Use an explicit shell argv, such as [cmd.exe, /D, /C, ...], when shell behavior is required.

Automatic .py entrypoint dispatch depends on the hook stage. See Hook Python dispatch for the authoritative interpreter order. An explicit command such as [python, scripts/build.py] deliberately uses PATH.

Variables

app-builder resolves variables in string values before schema validation. This makes config values reusable without giving up strict structure: interpolation can build strings, but it cannot inject lists, mappings, or new config keys.

Interpolation is for ordinary config values, not for choosing the app-builder implementation. app-builder reads app_builder_version before interpolation, so use a literal value such as current, a tag, a branch, or a commit there.

Surface How to use it Values
Windows environment expansion Use a supported percent-style root in installer.install_directory. %LOCALAPPDATA%, %APPDATA%, or %USERPROFILE%. Other variable-root install paths are rejected.
Release version Use --version, or omit it and let git provide the version. git describe --tags --always --dirty, falling back to 0.0.0-dev.
Hook environment Read environment variables from build, install, and uninstall hooks. app_builder_name, app_builder_version, app_builder_install_directory, app_builder_project_root, app_builder_start_menu.

Config Interpolation

Use ${...} inside any YAML string. Values such as ${GIT.DESCRIBE}, ${ENV.BUILD_NUMBER}, or ${CONFIG.installer.name} can be inserted into other strings after the YAML is parsed and before the config schema is validated.

Missing variables are errors. CONFIG.* references resolve recursively, so the target can itself contain ${...}. Circular references are rejected. The final CONFIG.* target must be a string; app-builder will not splice lists or mappings into YAML.

Use %LOCALAPPDATA%, %APPDATA%, or %USERPROFILE% for install paths that must resolve on the user's machine. ${ENV.*} is resolved while building the release, so it bakes in the builder or CI environment.

For Windows paths, single-quoted YAML strings are usually easiest because backslashes stay literal. If you use double-quoted YAML strings for Windows paths, write backslashes as \\.

Variable Meaning
${ENV.NAME} Environment variable from the running process, for example ${ENV.BUILD_NUMBER}. Lookup is case-insensitive on Windows.
${GIT.DESCRIBE} git describe --tags --always --dirty, using app-builder's version fallback when needed.
${GIT.COMMIT} Full current commit hash.
${GIT.SHORT_COMMIT} Short current commit hash.
${GIT.BRANCH} Current branch name when available, otherwise an empty string.
${GIT.TAG} Exact tag at HEAD when available, otherwise an empty string.
${GIT.IS_DIRTY} Boolean-like string indicating whether the worktree has uncommitted changes.
${APP.VERSION} The release version after --version or git detection. This is the best value for artifact names and install metadata.
${CONFIG.path.to.value} Another resolved string value from the same config. List indexes can appear in the path, but the final target must be a string. 
installer:
  name: "MyApp ${APP.VERSION}"
  install_directory: '%localappdata%\Acme\${CONFIG.installer.name}'
  paths:
    include:
      - "build/${APP.VERSION}"
    remap:
      - ["README.md", "docs/${CONFIG.installer.name}.md"]

Payload Files

installer.paths controls what goes into the installed app. Includes and excludes are project-relative globs. Remaps move files or directories inside the payload. 

installer:
  paths:
    include:
      - README.md
      - src_py
      - native
      - build/generated
    exclude:
      - build/generated/*.tmp
      - "**/__pycache__"
    remap:
      - [README.md, docs/README.md]
      - [src_py, py]
      - [native, sources/native]
      - [build/generated/app.cmd, bin/app.cmd]

app-builder also writes version.txt into the payload. That file is not used as an installer identity marker.

Materializing a Python runtime does not implicitly add it to the payload. If the installed app needs bundled Python, include its configured path, normally bin/python, in installer.paths.include. The project venv is normally build-only and should be included only when the installed application deliberately needs it.

Python Runtime

Python dependencies belong in pyproject.toml and are locked through Poetry. app-builder installs locked packages into Python runtimes configured for the project.

Mode Behavior
python_bundled enabled The complete Python.org Windows runtime is materialized under bin/python, including Tkinter, pip, venv, headers, and import libraries. Main dependencies are installed into that runtime. When selected for the installed payload, its pyvenv.cfg is relocated to the final install directory before post-install hooks run.
python_venv enabled with bundled Python A developer-owned venv is created from bundled Python. Required development dependencies are installed or updated in place, while packages added separately by the developer are retained.
python_venv enabled without bundled Python A developer-owned, self-contained venv is created from the complete Python.org Windows runtime. Main and development dependencies are maintained in place, while packages added separately by the developer are retained.
Both disabled No project Python is packaged. Build hooks can still use app-builder's own Python where the stage table allows it; installed-app hooks cannot.

Stable Python versions use an exact major.minor.patch pin. Python prereleases may use an exact form such as 3.15.0b4, or a release-level selector such as 3.15.0-beta. Normal builds verify an existing poetry.lock and install locked registry artifacts by SHA-256; use app-builder lock when dependency declarations change, and app-builder lock --check in CI to fail on a missing, stale, or invalid lock without rewriting it. Git sources require a full resolved commit. Mutable Poetry file and directory sources are rejected; publish a hashed artifact or use a pinned Git source instead. Complete Python runtimes are selected from Python.org's Windows runtime index, cached under %LOCALAPPDATA%\app-builder\cache\downloads by default, and verified against the SHA-256 published in that index.

python_bundled is reproducible release input: when its lock digest or dependency groups change, app-builder rebuilds it, including for an empty selection, so removed packages cannot survive into a later release. python_venv is the developer's additive working environment. Lock changes install or update required packages in place and leave unlisted packages alone. It is replaced only when its Python runtime is incompatible or structurally broken. Windows commands generated by pip use interpreter paths relative to the runtime, so runtime staging does not leave those commands tied to an old absolute path.

Hooks

Hooks let a project run its own commands at specific points in the pipeline, such as compiling files before packaging or producing additional release assets. Hooks are always argv lists. Use an explicit shell when shell behavior is required. 

build_hooks:
  pre_dist:
    - [scripts/generate_assets.py]
  post_dist:
    - [scripts/verify_dist.py]

Relative paths resolve from the project root for build hooks and from the staged or installed app for installer hooks. Existing .ps1 files run through PowerShell; other commands run directly as argv. An explicit command such as [python, scripts/build.py] deliberately uses the machine's PATH.

Build Hook Stages And Python

For an existing .py entrypoint such as [scripts/build.py], app-builder chooses Python by stage. "app-builder Python" means the interpreter currently running app-builder; it is available before the project runtimes have been created.

Hook Use it for Automatic .py interpreter order
pre_processEarly setup before dependency processing.app-builder Python
pre_python_bundledWork before bundled Python is materialized.app-builder Python
post_python_bundledWork after bundled Python and its main dependencies exist.bundled, then app-builder Python
pre_python_venvWork before the project venv is materialized.bundled, then app-builder Python
post_python_venvWork after the project venv and its development dependencies exist.venv, bundled, then app-builder Python
pre_distGenerate files that must be included in the payload.venv, bundled, then app-builder Python
post_distCreate extra outputs, verify the release, or sign the final installer after stale named outputs are cleared. The embedded payload and manifest are sealed.venv, bundled, then app-builder Python
pre_github_releasePrepare before GitHub upload.venv, bundled, then app-builder Python
post_github_releaseNotify, mark, or publish follow-up data after GitHub upload.venv, bundled, then app-builder Python

Installer hooks run on the user's machine, where app-builder itself is not present. Automatic .py dispatch for pre_install, post_install, and pre_uninstall uses the configured python_venv.path and then python_bundled.path interpreter included in the payload. These install-relative paths are recorded in the manifest, so custom runtime directories work without an explicit Python argv. post_uninstall runs after the install directory is removed, so its entrypoint must be a self-contained .cmd, .ps1, or .exe; .py is not auto-dispatched there.

Installer

app-builder release produces:

  • <slug>-<version>.zip: the payload.
  • <slug>-<version>.7z: the payload when installer.payload_format: 7z.
  • <slug>-<version>-installer.exe: the self-extracting installer.
  • <slug>-<version>-manifest.json: the build manifest.
  • <slug>-<version>-SHA256SUMS.txt: hashes for every resolved release output.
  • <slug>-<version>-release-notes.md: generated release notes for publication.

Named outputs can collect exact files or bounded filename globs created under installer.dist. publications.github.outputs then selects the built-in and named outputs uploaded to GitHub. Existing files matching those declarations are removed before post_dist, so only outputs produced by the current build can be collected. Match counts, duplicate paths, and GitHub filename collisions are enforced.

Output names, patterns, bounds, and publication selections are checked before dependencies or hooks run. Set min_matches: 0 only for a genuinely optional asset. The logical output remains selectable when no file matches and contributes no GitHub asset for that build. 

build_hooks:
  post_dist:
    - [scripts/build_wheels.py]
outputs:
  - name: wheels
    pattern: wheels/*.whl
    min_matches: 1
    max_matches: null
publications:
  github:
    outputs: [installer, manifest, checksums, wheels]

installer.payload_format selects the inner payload archive. zip is the default. 7z uses bundled 7-Zip files in the outer installer layer and preserves remapped paths plus Windows locked-file staging.

Both payload formats reject paths that can leave the extraction root, Windows-reserved names, generated paths such as version.txt, case-insensitive destination duplicates, and file/directory collisions before archive creation begins.

installer.dist is excluded from the payload by default even when a broad include selects it. installer.paths.include_dist: true is the explicit opt-in for the unusual case where release output belongs inside the installed application. Shortcut targets and explicit icons must resolve to real final payload paths after remapping.

installer.icon is optional. When configured, it is embedded into generated executables. A Start Menu shortcut with an omitted or null icon inherits it, and app-builder includes the icon automatically at its normal project-relative path or configured remap. With no installer icon, or with an empty shortcut icon, IconLocation is left unset so Windows uses the target executable or file-type icon.

The installer extracts its outer ZIP layer to a random temp directory, runs the PowerShell installer, forwards all command-line arguments, and removes its temp extraction directory when finished. If an environment blocks running the exe, the manual fallback is: rename the installer to .zip, extract it, and run install.cmd.

Runtime Flags

Flag Behavior
--yes Bypass confirmation questions and skip the final close wait.
--no-wait Skip only the final close wait.

When installer.wait_on_exit is true and no bypass flag is supplied, the console closes after 30 seconds or when the user presses Enter. Other keys are ignored.

When installer.add_uninstaller is enabled, installation writes a per-user Windows Installed Apps record with interactive and quiet uninstall commands. The cleanup worker removes that record after the install directory has been removed.

post_install runs only after payload files, shortcuts, installed uninstall scripts, and the Windows Installed Apps record are in place. If it fails, the installer rolls those changes back and restores a recognized previous installation.

Existing Directory Rules

Existing directory Behavior
Current app-builder install for the same app Runs old pre_uninstall, moves the old install to a backup sibling, installs the new payload, and restores on failure.
Recognized legacy app-builder install for the same app Runs recognized legacy pre-uninstall hooks, moves the old install to a backup sibling, installs the new payload, and restores the legacy directory and Windows integration if replacement fails.
Different app-builder app Refuses to overwrite.
Unknown directory Refuses to overwrite. Files such as version.txt, python-version.txt, and gitinformation.json are not install markers.

Uninstall

By default the installer writes bin\uninstall.cmd and bin\uninstall.ps1 into the installed app and creates an Uninstall <app name> Start Menu shortcut that points to the installed bin\uninstall.cmd.

The PowerShell uninstaller infers the install root from its own location, not from the manifest's install_directory. Uninstall runs pre_uninstall while the app is still present, removes Start Menu entries, stages allowed post_uninstall entrypoints, removes the install directory, then runs post_uninstall.

If a post_uninstall command points inside the install directory, its entrypoint must be a self-contained .cmd, .ps1, or .exe. Do not rely on helper files that will be deleted before the command runs.

Releases

Local releases are artifact generation only. GitHub releases use gh.exe. 

app-builder release --version 1.2.3
app-builder release-gh --version 1.2.3
app-builder release-gh --version 1.2.3 --draft

Publication uploads exactly the built-in and named outputs selected by publications.github.outputs. Generated release notes become the GitHub release body. A new release targets the exact commit recorded when its artifacts were built. An existing tagless draft is retargeted to that verified commit. Existing releases upload replacements and refresh metadata before stale assets are removed. --draft controls creation of a new release; updating an existing release preserves its current draft or published state.

Before upload, app-builder requires a clean Git worktree outside installer.dist, validates version, build-commit, and local/GitHub tag identity, verifies the manifest, outer installer layout, artifact inventory, and SHA-256 checksums, and confirms that gh.exe is authenticated for the repository. The standalone payload must match the bytes embedded in the installer, and the published manifest must match the manifest embedded in its scripts. Every GitHub command is pinned to the repository resolved by preflight, so an ambient GH_REPO cannot redirect publication. For app-builder itself, the release version must match pyproject.toml.

app-builder searches where.exe, PATH, and common GitHub CLI install locations. Install and authenticate GitHub CLI with: 

winget install --id GitHub.cli
gh auth login

Builds announce eight timed stages immediately. A timestamped log under <dist>/build-logs records the complete payload map, dependency provenance, output hashes, and publication selection. Add --verbose to mirror those details to the terminal.

Reusable Caches

app-builder caches reusable Python and ExeWrap archives and managed app-builder versions. On Windows the root defaults to %LOCALAPPDATA%\app-builder\cache; on other platforms it follows XDG_CACHE_HOME and then ~/.cache/app-builder. Cache placement is machine policy, not part of the application release contract, so it is intentionally not an app_builder.yaml setting.

Set APP_BUILDER_CACHE_ROOT when CI needs one stable directory to restore. Explicit PIP_CACHE_DIR and POETRY_CACHE_DIR values retain control of those tools. Otherwise, when the app-builder root is explicitly set, its pip and Poetry subprocesses use <root>/pip and <root>/poetry. Without an explicit app-builder root, pip and Poetry keep their native defaults. 

env:
  APP_BUILDER_CACHE_ROOT: ${{ runner.temp }}/app-builder-cache

steps:
  - uses: actions/cache@v4
    with:
      path: ${{ env.APP_BUILDER_CACHE_ROOT }}
      key: app-builder-v1-${{ runner.os }}-${{ hashFiles('poetry.lock', 'app_builder.yaml') }}
      restore-keys: |
        app-builder-v1-${{ runner.os }}-

Downloads are separated by URL-derived keys, written to private temporary siblings, digest-checked when a digest is published, and atomically promoted under a cross-process lock. Failed downloads cannot poison a later build. Use app-builder cache path for scripts and app-builder cache info to inspect the resolved layout.

App-builder-owned settings use the APP_BUILDER_ namespace. Unknown names produce one warning, with a spelling suggestion where possible, and their values are never printed. Set environment variables before the first app-builder command in a process.

app-builder Versions

app_builder_version controls which app-builder implementation runs for the project:

Value Behavior
missing, blank, or currentUse the installed 1.x app-builder.
1.6.0, branch, or commitCheck out that ref into the managed version cache and run it.
0.x or v0.*Error. Use app-builder 0.x <command>.

Managed versions are cached under the common app-builder cache root. Cache keys include the source URL and requested ref. A branch is refreshed when its remote commit changes; a moved cached tag is refused. Cache creation is locked per ref, built privately, and atomically promoted, so concurrent commands cannot consume a partial cache. Use app-builder versions list to inspect manifests and app-builder versions remove <ref> for deliberate eviction.

A managed version installs the exact non-optional main dependencies from that commit's poetry.lock with artifact hash checking. The checked-out app-builder source runs directly; ranged project dependencies are never re-solved for the cache. Its manifest records the commit and lock digest.

Legacy Projects

Old projects that still use application.yaml are not run automatically by 1.x. Use: 

app-builder 0.x <command>

The compatibility bridge is built from the old app-builder source with scripts/build_legacy_0x_bridge.py. It is intentionally isolated from the 1.x package.

A project that has already migrated to app_builder.yaml may retain a minimal application.yaml solely so an already-installed 0.x launcher can forward into a 1.x tag: 

app_builder: 1.5.0
# Compatibility shim for installed app-builder 0.x launchers.
# The real project configuration is app_builder.yaml.

The old launcher creates its normal version cache, installs the selected 1.x ref's compatibility-only root requirements file, and then runs the 1.x CLI against app_builder.yaml. The helper is inert outside that exact legacy cache layout and does not replace the outer app-builder installation.

The forwarding helper is installed from its local source directory, never by package name. Its requirements are exact versions derived from the selected ref's committed poetry.lock. The separately bundled 0.x runtime is pinned to the v0.20.0 commit and built from committed hash-checked dependency locks.

Troubleshooting

No config found

Run app-builder init in a git repository, or move into a project that already contains app_builder.yaml.

Legacy config found

If the project still has application.yaml, use app-builder 0.x <command> or migrate to app_builder.yaml.

Python hook cannot run

Build hooks use the interpreter order in Build Hook Stages And Python. For an installer hook, make sure a configured project runtime and its interpreter were included in the payload. The build fails when automatic .py hooks have no packaged interpreter. For post_uninstall, use a self-contained .cmd, .ps1, or .exe. An explicit [python, ...] command intentionally depends on PATH.

Config interpolation failed

Check the exact variable name and the final value type. ${ENV.*} needs an environment variable that exists, ${GIT.*} needs a readable git repository, and ${CONFIG.*} must point at another string value without forming a cycle.

Python runtime version missing

Pin an available stable version such as 3.12.10, or a Python prerelease such as 3.15.0b4. A selector such as 3.15.0-beta chooses the latest matching beta.

GitHub release failed

Confirm gh.exe is installed and authenticated with gh auth status.

Installer refuses an existing directory

The directory is not recognized as a current or legacy app-builder install for the same app. Choose a clean install directory or remove the old directory deliberately.

Upgrade is blocked by a locked file

Close the running application and retry. If Windows cannot move the existing install to its backup sibling, app-builder stops before replacing it and leaves the old install in place; it does not force unlock files, request elevation, or schedule deletion after restart.

Installer executable is blocked

Rename the installer from .exe to .zip, extract it with Windows, and run install.cmd. The installing machine still needs PowerShell and tar.exe for the supported installation path.

Uninstall leaves diagnostics in temp

Failed asynchronous post-uninstall cleanup writes an error.txt in its temp staging directory so the failure is not lost.
