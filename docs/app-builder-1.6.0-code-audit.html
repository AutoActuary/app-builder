Verdict

Do not publish the next release yet.

The normal test suite is healthy, but the audit found failures outside its current assertions. The most serious are destructive legacy-upgrade rollback, install-root traversal, release identity drift, a dependency-confusion path in the 0.x bridge, and non-reproducible runtime materialization.

This is not a rewrite verdict. Archive safety, payload sealing, current-1.x rollback, cache locking, manifest integrity, and the normal ZIP and 7-Zip paths held up well. The required work is concentrated and testable.

Release blockers

P1A failed 0.x upgrade destroys the old installation

installerrollbackdata loss

A recognized current 1.x installation is moved to a sibling backup before replacement. A recognized legacy installation is instead removed immediately. If any later step fails, including post_install, rollback removes the new files but has no legacy backup to restore.

Reproduction: a generated installer was run against a recognized legacy-shaped directory with a new post_install hook that exits 19. The installer returned failure and left neither the legacy files nor the replacement directory.

Source: installer_bundle.py:338-397. Existing tests cover current-install rollback and a failing legacy pre-uninstall hook, but not failure after legacy removal.

Fix direction: preserve the validated legacy directory and its Windows integration state until every new-install step succeeds. Restore both on failure. Add a real Windows regression that fails after legacy removal.
Implementation: recognized 0.x directories now use the same private sibling-backup transaction as current installs. Legacy registry and shortcut cleanup is deferred until the replacement and post_install succeed; rollback restores the old directory and untouched integration. Windows tests cover successful adoption and failure after legacy removal.

P1Variable-root install paths can escape their approved root

installerpath safetyuninstall authority

The preflight accepts a leading approved variable and returns before checking .. components or the normalized destination. The installer later expands and canonicalizes the path, so a value that appears user-scoped can resolve to C:\, C:\Windows, or C:\ProgramData. The resulting uninstaller treats that resolved directory as its deletion root.

Reproductions: %USERPROFILE%\..\..\Windows\Demo passed preflight and resolved to C:\Windows\Demo. C:\harmless-name\.. also passed and normalized to the drive root.

Source: build_preflight.py:97-159; runtime normalization in installer_bundle.py:549.

Fix direction: reject dot segments, expand known variables during release preflight, require the normalized target to be a strict child of the permitted user root, and repeat the invariant inside the generated installer.
Implementation: build preflight rejects parent-directory components before accepting variable or fixed roots. The generated PowerShell installer independently expands and canonicalizes the final user-machine path, requires variable-root targets to remain strict children, and rejects filesystem and protected Windows roots.

P1Installer EXEs fail when their path contains an apostrophe

ExeWrapPowerShellfirst launch

The ExeWrap bootstrap inserts @{exe_path} directly into a PowerShell single-quoted literal. Apostrophes in a user profile or download directory terminate that literal before extraction begins.

Reproduction: a real generated installer launched from an O'Brien directory exited 1 with The string is missing the terminator: '.

Source: installer_bundle.py:144.

Fix direction: carry the executable path through an ExeWrap JSON-safe value or environment value and read that value in PowerShell. Add final-EXE tests for apostrophes, spaces, brackets, Unicode, and trailing punctuation.
Implementation: ExeWrap now places @{exe_path} directly in the child environment. PowerShell passes that environment value to tar.exe as an argument, so the path is never inserted into PowerShell source. A real final installer test runs from an apostrophe-containing directory.

P1The generated starter config cannot build its own payload

initfirst useconfig contract

The generated paths.include list omits README.md, while the same generated config requires a remap from README.md to docs/README.md. The remap validator correctly refuses a source outside the selected file set.

Reproduction: after generating the documented assets and providing the runtime placeholder, payload mapping failed with Payload remap source is not present in the resolved file set.

Source: schema.py:75-100; enforcement in fileset.py:114.

Fix direction: include README.md in the generated selection or remove the example remap. Add an acceptance test that runs init and then builds the generated project without hand editing.
Implementation: the schema-generated starter include list now selects README.md. The initialization test creates the full required fixture and proves the generated remap resolves to docs/README.md.

P1init --force overwrites customized application assets

initdata loss

The CLI describes --force as overwriting the template config. The implementation also unconditionally replaces every file under application-templates, including a customized launcher and icon.

Reproduction: modify application-templates/program.cmd, run forced initialization, and the packaged default silently replaces the custom file.

Source: template.py:222-238; option help in main.py:69.

Fix direction: make config replacement and starter-asset replacement separate explicit choices. Never overwrite an existing asset under the current --force contract.
Implementation: --force now replaces only app_builder.yaml. Starter files are copied only when absent, and tests preserve customized program.cmd and icon.ico bytes.

P1The 0.x compatibility bridge can be replaced by an index package

supply chain0.x bridgepip

The root requirements file adds the local bridge with --find-links and then asks pip for app-builder-0x-version-bridge==1.0.0 by name. This does not require the local candidate. An index wheel with that name and version can win resolution. The package name was unclaimed on PyPI at audit time.

Reproduction: an isolated pip solve containing a local bridge candidate and an index-style wheel with the same name/version selected the wheel rather than the local source.

Source: requirements.txt:3 and bridge-links.html:5.

Fix direction: use a direct relative requirement that identifies the local bridge itself. Do not resolve this compatibility shim by a public package name.

P1Published artifacts are not bound to the commit that built them

release-ghprovenance

Artifacts are assembled before pre_github_release. Publication preflight later validates the current clean HEAD, but the sealed manifest does not record and verify the build commit. A hook or concurrent process can commit B after artifacts were built from A, causing A's bytes to be published against B.

Reproduction: artifacts and notes were built at commit A, commit B was created without rebuilding, and publication preflight accepted the unchanged artifacts at B.

Source: build.py:724-747 and release_preflight.py:93.

Fix direction: record the exact build commit in the manifest and release result, then require publication HEAD and the tag target to equal it.

P1GitHub validation and upload can address different repositories

release-ghrepository identity

Preflight resolves a repository with gh repo view, but later gh release calls omit --repo. An ambient GH_REPO can therefore redirect release reads and mutations away from the repository that was validated.

Reproduction: in this worktree with GH_REPO=cli/cli, gh repo view resolved AutoActuary/app-builder while gh release list addressed cli/cli.

Source: build.py:766-864.

Fix direction: normalize one repository identity during preflight and pass it explicitly to every view, create, upload, edit, and asset-delete command.

P1An existing draft can keep an obsolete target commit

release-ghdraft release

Existing release metadata requests only URL and assets. When a tagless draft already targets commit A and the project advances to B, app-builder uploads B's outputs and edits title/notes without inspecting or updating targetCommitish.

Trace: the current gh release view request omits targetCommitish, and gh release edit omits --target. Remote tag validation returns early when the tag does not yet exist.

Source: build.py:777-840.

Fix direction: inspect draft status and target. Update a tagless draft to the verified build commit or reject the mismatch before uploading.

P1Removed dependencies survive into later releases

Python runtimereproducibilitystale code

Existing bundled and venv runtimes are reused when their Python marker matches. Dependency materialization only installs packages currently selected by poetry.lock. It never removes packages deleted from the lock, and returns immediately when the selected set is empty.

Reproduction: a disposable runtime containing obsolete_dependency was materialized against an empty lock. The package remained importable before and after. The manifest would record only the new lock while the payload retained old code.

Source: poetry_dependencies.py:146-197; runtime reuse in python_runtime.py:747-784.

Fix direction: key environments to the selected lock digest and rebuild them atomically when it changes, or reconcile installed distributions against an exact lock inventory. Add consecutive-build tests.

P1Immutable source refs still resolve mutable dependency graphs

managed versions0.x bridgereproducibility

A cold managed-version cache upgrades pip and installs the checked-out repository using ranged project dependencies instead of that ref's committed lock. The dogfood 0.x bridge also checks out a tag without an expected commit and installs wildcard legacy requirements without hashes. Rebuilding one immutable tag at different times can produce different executable environments.

Reproductions: a clean managed install of tag 1.6.0 selected Click 8.5.0 while its poetry.lock records 8.4.1. The generated bridge contained 18 independently resolved distributions not represented in the release manifest.

Source: version_cache.py:104-121 and build_legacy_0x_bridge.py:43-63.

Fix direction: define committed, hash-checked bootstrap constraints for managed versions and the bridge; install the repository itself with --no-deps; pin the 0.x commit; record dependency-input digests in the build manifest.

Secure default needs a decision

Both Python runtime sections still default to 3.11.1 from December 2022. Python 3.11.16 is the current security release, and 3.11 is now security-fixes-only. Because app-builder requires an exact version for reproducibility, the clean contract is likely to require python_version whenever a runtime section is enabled, rather than silently choosing an old patch. See schema.py:26-42 and the Python 3.11.16 release.

Known limits and rejected candidates

Known: uninstall completion is asynchronous

The uninstaller returns success after launching a detached cleanup worker. A later locked-file or post_uninstall failure cannot change the caller's exit code; the worker leaves temp diagnostics. The test suite explicitly asserts this behavior. This was already documented as an accepted limitation, so it is not counted again as a new defect, but automation cannot treat exit 0 as proof of completed removal.

installer_bundle.py:1209-1324; test_installer_failure_modes.py:716-778.

Known: unsigned installers can trigger reputation systems

Open issue #76 records a Defender ML detection that later rescanned clean. The published bytes and digests matched, but releases are not Authenticode signed. Signing and a final Defender scan remain release-process hardening, not proof of a source defect.

Rejected: a modified cache manifest can name another executable

The managed cache trusts its own manifest paths. This is worth containment hardening, but it was not counted as a security blocker because the cache is private user-writable state. A same-user actor able to replace that manifest can already replace the launcher, cached Python, or checkout. Treat invalid containment as cache corruption and rebuild it.

No defect found in archive containment

ZIP and 7-Zip destination validation rejects traversal, absolute paths, Windows reserved names, case-insensitive collisions, and parent file/directory collisions. Safe extraction and embedded-payload equality also held.

Audit method

Rule used throughout: first-pass suspicion is not a finding. A finding needed a complete source-to-effect path plus a reproduction, an executable test, or a cross-file proof that survived challenge.

No single guide is the whole state of the art. This audit combined the strongest current practices from repository-level agent research, secure code review, threat modeling, and agent-review guidance:

  1. Model the whole system. Map entry points, trust boundaries, persistent state, generated code, network inputs, and irreversible actions before reviewing functions.
  2. Use independent specialist passes. Six reviewers were assigned installer lifecycle, config and execution, release and supply chain, public contract, tests and performance, and an adversarial whole-repository pass. Two were stopped by an automated classifier; five completed, including the whole-repository pass.
  3. Trace across files. Follow data from config or environment through validation, generated PowerShell, filesystem/registry mutation, cache reuse, and GitHub CLI calls.
  4. Validate path feasibility. Reproduce on Windows or in disposable repositories and environments. Measure performance claims rather than inferring them from loop shape.
  5. Challenge false positives. Deduplicate common root causes, distinguish same-user cache trust from a crossed boundary, and keep accepted limitations separate.
  6. Report for repair. Every finding identifies workflow, effect, evidence, source, fix direction, and missing regression test.

Primary references: RepoAudit, ICML 2025, Codex Security, OWASP Secure Code Review, OWASP Threat Modeling, GitHub agent code review guidance, and How OpenAI uses Codex.

Coverage and verification

Local gates

  • 215 unit and Windows integration tests passed in 49.7 seconds.
  • Black passed on 62 files.
  • MyPy passed on 61 source files.
  • compileall and pip check passed.
  • The worktree started clean at the exact 1.6.0 commit.

Focused validation

  • Real Windows installer failure and legacy rollback.
  • Real ExeWrap launch beneath an apostrophe path.
  • Disposable runtimes, managed caches, wheels, and Pydantic environments.
  • Throwaway Git repositories and mocked GitHub release failure boundaries.
  • Payload validation timing through 32,000 files.

Areas that held up

Archive traversal and collision defenses, safe Python ZIP extraction, payload sealing, installer/payload/manifest byte equality, checksums, current-1.x install rollback, cache locking and atomic cache promotion, version/tag/package identity for 1.6.0, packaged template/help inclusion, strict unknown-key loading, and ZIP/7-Zip normal paths.

External tests not performed

No live GitHub release was mutated. No UAC/elevated install, ARM Windows, x86 Windows, code-signing flow, or hostile network proxy was exercised. The final public 1.6.0 installer was not re-published.

Recommended fix order

  1. Stop destructive or unsafe installation. Fix legacy rollback, canonical install-root enforcement, and ExeWrap apostrophe handling. Add real final-EXE tests first.
  2. Bind publication identity. Seal build commit and repository identity, validate draft target, and reorder existing-release reconciliation.
  3. Make dependency materialization deterministic. Fix local bridge selection, stale package removal, managed-version locks, and bridge locks.
  4. Repair first-use contracts. Make generated config build, make init non-destructive, and handle all accepted config filenames.
  5. Unify schema behavior. Resolve prerelease validation, Pydantic 1 support, exported constraints, and optional-output semantics.
  6. Harden runtime operations. Lock and atomically promote runtimes, disambiguate free-threaded packages, add network deadlines, and optimize payload validation.
  7. Regenerate and verify all docs. Fix local help lookup, examples, and cache locations, then run docs snapshot and wheel-install tests.
Release gate: all P1 findings fixed with regression tests; P2 findings either fixed or explicitly accepted in release notes; full Windows suite, final ZIP and 7-Zip installer rehearsals, managed-version cold start, 0.x bridge dispatch, and a dry-run GitHub publication contract test pass from a clean clone.
