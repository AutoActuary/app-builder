Release readiness: implementation complete, Windows CI still deferred

app-builder 1.x can build, install, replace, and uninstall real Windows packages. It is no longer scaffolding. The implementation branch closes the audited code-level security, Windows integration, packaging, reproducibility, and release-process gaps; enforcing the installer matrix in Windows CI remains deliberately deferred.

Python is the supported built-in runtime; other build systems remain possible through hooks instead of returning the old collection of special cases.

Release blockers

P0ZIP remaps can escape the archive root or collide

The 7-Zip writer validates archive destinations, but the ZIP writer sends each remapped destination directly to ZipFile.write. The common remap table also does not reject absolute paths, .. segments, or two sources mapped to the same destination.

A focused audit build produced a ZIP containing ../outside.txt. A second build accepted two same.txt members and emitted only a duplicate-name warning. This is both a package integrity failure and a potential extraction traversal vulnerability.

Fix: move destination validation into build_remap_table, validate every format, reject collisions before writing, and add equivalent ZIP and 7-Zip tests.

Implementation: implemented on codex/1x-release-blockers. A shared validator now runs before either archive writer and rejects traversal, absolute and Windows-unsafe paths, reserved generated files, case-insensitive duplicate destinations, and file/directory collisions. Direct validator tests and a full ZIP release regression test cover unsafe, duplicate, and reserved remaps.

Source: fileset.py:42, build.py:252, sevenzip.py:117.

P0The Windows installer is not exercised by Windows CI

Every workflow runs on ubuntu-latest. The tests contain 16 Windows skip decorator sites, covering real ExeWrap execution, PowerShell installation, icon resource updates, 7-Zip execution, rollback and failure modes, and end-to-end installation.

The local Windows run is encouraging, but it is not a repeatable release control. A Windows-first installer cannot be signed off by Linux checks that skip its defining behavior.

Fix: add a windows-latest job that runs the full suite and a release-smoke job that builds and launches the actual installer EXE, not just extracted scripts.

Implementation: not implemented in this branch. This is deliberately deferred to a separate follow-up branch, proposed as codex/1x-windows-ci, so workflow permissions, runner cost, artifact retention, and the real-EXE smoke matrix can be reviewed independently. No claim of CI coverage is made by the blocker implementation branch.

Source: test.yml:13, test_installer_bundle.py, test_installer_failure_modes.py.

P01.x does not register itself in Windows Installed Apps

The installer creates a Start Menu uninstall shortcut but never writes an uninstall registry record. The documentation currently says it does. Windows Settings therefore cannot discover a normal 1.x installation as an installed app.

Legacy cleanup is also too exact: it deletes the registry key named exactly like the new manifest and the Start Menu directory computed from the new name. It misses historical identities such as App Builder and vendor folders such as AutoActuary\App Builder. That matches the stale entry already observed on this machine.

Fix: write a proper HKCU uninstall record for every 1.x install, remove it on uninstall, and discover legacy entries by normalized identity plus validated uninstall target rather than guessed exact paths.

Implementation: implemented on codex/1x-release-blockers. Installer-enabled apps receive a stable per-user uninstall key derived from the canonical install path, with display identity, install location, interactive PowerShell uninstall, and quiet --yes uninstall values. Upgrade failure restores the prior 1.x record, the cleanup worker removes the record after directory deletion, and legacy registry entries and Start Menu uninstall links are removed only when normalized identity and target path both match. A real HKCU install/uninstall test verifies the full lifecycle.

Source: installer_bundle.py:260, 978; stale claim: app-builder-help.html:218.

P0Release version and installed CLI version can disagree

The release command accepts any --version and uses it in filenames and the installer manifest, while package metadata and app_builder.__version__ remain static. The audit installer announced 1.2.1-audit, then the installed app-builder --version reported 1.2.0.

The public 1.2.0 tag also points one commit behind the current 1.x head. There is no preflight enforcing branch, clean tree, tag target, package version, generated version, and release version as one identity.

Fix: establish one version source and fail release when any derived identity differs. The release command should verify HEAD, tag target, clean tracked tree, and CI status before publication.

Implementation: implemented on codex/1x-release-blockers. The installed app-builder CLI resolves its version from the installed manifest, eliminating the installer/CLI mismatch. Wheel and source installs fall back to package metadata instead of a second hard-coded constant. Publication additionally requires app-builder's pyproject.toml version to equal the requested release and rejects local or authenticated GitHub tags that point anywhere other than the audited HEAD. CI status remains part of the separately deferred Windows CI blocker.

Source: pyproject.toml:7, app_builder/__init__.py:9, build.py:40.

P0The installable Python package loses its help document

The project is installable as a wheel, and app-builder init works from that wheel. However, top-level docs is not package data. The first line of --help therefore links to a file that is absent in an ordinary wheel installation.

Fix: package the HTML under an importable resource directory and resolve it with importlib.resources, or provide a tested durable web URL with an offline bundled fallback. Test both wheel and app-builder installer layouts.

Implementation: implemented on codex/1x-release-blockers without reintroducing a duplicate help file. Setuptools installs the single docs/app-builder-help.html source under share/app-builder/docs; the CLI checks the app-builder installer layout first, then the wheel data location, and finally uses the repository help URL as a fallback. Unit and isolated wheel-install checks cover the packaged path.

Source: pyproject.toml package-data, main.py.

P0Publication has no enforceable release preflight

GitHub publication uploads three hard-coded files. A new release gets an empty note body; an existing release has selected assets clobbered but keeps old metadata and any stale extra assets. There is no checksum set, provenance file, signing check, branch rule, clean-dist staging area, or CI gate.

The current dist directory contains multiple 1.1.0 variants and 1.2.0 files because builds do not clean old output. The hard-coded uploader reduces accidental upload risk, but local inspection and manual release work remain ambiguous.

Fix: add a release plan object and preflight. Build into a version-specific staging directory, generate release notes and SHA-256 checksums, fail on version/tag mismatch, and make existing release reconciliation explicit.

Implementation: implemented on codex/1x-release-blockers. Local releases now create generated notes and a SHA-256 checksum file. Before publication, app-builder enforces a clean source tree outside dist, valid release/tag identity, app-builder package-version agreement, exact nonempty artifact inventory, matching manifest and payload, readable outer installer layout, verified checksums, authenticated gh.exe, and an authenticated GitHub tag that is absent or points to HEAD. New releases target that exact commit; existing releases replace intended assets, delete stale assets, and refresh title and notes. CI gating and code signing remain separately visible work rather than being implied by this preflight.

Source: build.py:365.

Product completeness gaps

P1Multiple release assets are still a design, not a feature

ReleaseResult contains exactly one payload, one installer, and one manifest. GitHub upload hard-codes those three. Hooks may create extra files, but app-builder cannot discover, name, validate, relate, or publish them.

This blocks the earlier Autory goal: several related artifacts in one version, including outputs built by non-Python tools and artifacts renamed by post-build work. The missing abstraction is an output collection, not another special installer option.

Required: named outputs, deterministic path or constrained glob pickup, required match counts, collision detection, per-output metadata, and publication groups. The release result and GitHub publisher should consume the resolved output set.

Implementation: implemented on codex/1x-release-blockers. Projects can declare named output collections using exact paths or constrained, non-recursive filename globs beneath installer.dist, with minimum and maximum match counts. Resolution is deterministic and rejects unsafe patterns, reserved names, duplicate paths, and GitHub filename collisions. Each resolved file carries its logical name, size, and SHA-256 digest; publications.github.outputs expands exact logical names into the upload set, and checksums plus publication preflight cover every resolved release output.

P1Hook lifecycle has an ordering contradiction

post_process runs inside build_release, before release-gh starts its GitHub hooks and upload. Documentation describes it as end-of-release or final local cleanup. Both meanings cannot be true for GitHub publication.

Required: name and document separate build-finalization and command-finalization hooks, or move orchestration to one release pipeline that runs final cleanup exactly once after the selected publication target completes.

Implementation: implemented on codex/1x-release-blockers by removing post_process from the schema, runtime, generated template, tests, and documentation. post_dist remains the final local artifact hook before output collection, checksums, and release notes; post_github_release remains the unambiguous hook after successful GitHub publication.

P1Dependency materialization is not reproducible enough

Every dependency run executes poetry lock, which may mutate the project and re-resolve rather than verify a committed lock. Installation then reconstructs name==version requirements and uses pip --no-deps without Poetry artifact hashes. Python runtime inputs lack an enforced upstream digest, and self-contained venv launchers resolve the latest ExeWrap release at build time.

Required: verify an existing lock by default, add an explicit lock-refresh command, preserve and require artifact hashes where available, pin external runtime/launcher inputs, and record all selected digests in the release manifest.

Implementation: implemented on codex/1x-release-blockers. Normal dependency and release commands now require an existing poetry.lock and verify it with poetry check --lock without mutation; app-builder lock is the sole explicit refresh command. Registry and URL packages install from a temporary requirements file with Poetry's SHA-256 hashes under pip --require-hashes, while Git packages require a full resolved commit. Python.org runtime packages are verified against the runtime index's SHA-256, ExeWrap is pinned to v2.1.0 with per-architecture SHA-256 digests, and the installer manifest records the selected lock, runtime, and launcher provenance.

Source: poetry_dependencies.py:65, python_runtime.py:346, 373, 822.

P1Managed version caching needs a user-level contract

The cache defaults under the installed package root. That works for the dogfood per-user installer but can be unwritable for a normal system Python installation. A cached branch ref is returned forever without checking whether the remote moved, and sanitized ref names can collide.

Required: use a user-local cache root by default, include a hash in the cache key, make tags immutable, define refresh behavior for branches, and record source URL, requested ref, and resolved commit in the manifest.

Implementation: implemented on codex/1x-release-blockers. Managed versions now live under the writable per-user app-builder cache, overridable with APP_BUILDER_CACHE_ROOT, while the installation root remains solely responsible for the bundled 0.x bridge. Cache directory names combine a readable ref slug with a hash of source URL and exact ref. Every invocation fetches the shared source: branch caches rebuild when their remote commit changes, commit caches remain content-addressed, and a moved cached tag is refused. Manifests record source URL, ref kind, requested ref, resolved commit, and timestamps; app-builder versions list/remove exposes cache inspection and deliberate eviction.

Source: version_cache.py:25, 46, 112, 137.

P1Config is structurally strict but not operationally defensive

Unknown keys and wrong types are rejected, which is excellent. Operational checks remain thin: include patterns and remap sources may match nothing, duplicate destinations are accepted, dangerous install roots are not rejected early, and version/name strings are not fully validated for Windows filenames and release tags.

Required: add a preflight that prints the resolved file set and fails on missing required inputs, empty payloads, unsafe install targets, unsafe archive destinations, collisions, and invalid release identity.

Implementation: implemented on codex/1x-release-blockers. Build preflight now rejects unsafe Windows names and release refs, root-like or unsupported install targets, non-exact Python runtime pins, empty hook commands, unmatched includes, empty payloads, and missing or unselected remap sources. Dist, bundled-Python, and venv write paths must resolve to project subdirectories; protected Windows install trees are rejected. File and remap resolution stays inside the project, while the existing archive destination and collision validator remains the final archive boundary. Every resolved source-to-archive mapping is written to the build log before archive creation.

P2Clean builds are opaque and noisy

The clean dogfood build produced no visible progress for roughly three minutes because subprocess output was buffered, then released a large block of pip output. This will be mistaken for a hang during a real release.

Required: print named stages with elapsed time, stream or summarize long subprocesses, and keep a verbose log file for diagnosis.

Implementation: implemented on codex/1x-release-blockers. Local and GitHub releases now print eight immediate stage transitions with elapsed times and explicit failure context. Pip runs quietly with progress bars disabled, while a timestamped log under dist/build-logs retains resolved payload mappings, pinned build inputs, output sizes, SHA-256 digests, and publication selection. --verbose mirrors those details to the terminal.

Road to 100%

“100%” here means every declared 1.x contract has a repeatable release gate. It does not mean no defect can ever exist. The work should land in this order so later tests and documentation lock down the correct behavior.

Gate 1: archive and install safety

Current: code complete; the real-installer matrix still needs Windows CI enforcement.

  1. Centralize archive destination validation for ZIP and 7-Zip.
  2. Reject path traversal, absolute destinations, reserved destinations, and duplicate mappings.
  3. Fail on missing required includes/remap sources and an effectively empty payload.
  4. Reject clearly dangerous install roots before extracting or moving anything.
  5. Add the 1.x HKCU uninstall record and remove it transactionally.
  6. Replace exact legacy registry/Start Menu guesses with normalized identity discovery and target validation.

Gate 2: real Windows CI

Current: deliberately deferred to a separate branch.

  1. Run the full suite on windows-latest with the shipped Python baseline.
  2. Build a small installer, launch the real EXE with --yes, run its application, replace it, and uninstall it.
  3. Exercise ZIP and 7-Zip, spaces and apostrophes in paths/arguments, locked files, hook failures, rollback, legacy adoption, and post-uninstall behavior.
  4. Upload the smoke installer and logs when a job fails.

Gate 3: coherent release identity and publication

Current: identity, artifact, tag, worktree, and GitHub preflight are implemented. Required-check policy and code signing remain release-owner work.

  1. Create one version source for package metadata, CLI, manifest, filenames, tag, and release title.
  2. Add preflight for clean tracked tree, expected branch, tag target, green required checks, and exact artifact inventory.
  3. Build in a clean version-scoped directory and generate release notes, SHA-256 checksums, and provenance.
  4. Decide and implement the code-signing policy before team-wide promotion.
  5. Make existing-release updates explicit: metadata, notes, intended asset replacement, and stale asset removal.

Gate 4: packaging and documentation

Current: implemented; generated references and packaged help paths are covered by tests.

  1. Make the help HTML an installed package resource and test it from both a wheel and the app-builder installer.
  2. Correct known false claims and hook examples.
  3. Generate schema reference fragments from one source and snapshot-test every generated destination.
  4. Publish a concise user journey, support matrix, troubleshooting guide, and release operator checklist.

Gate 5: finish the multi-asset 1.x model

Current: named output resolution, explicit publication selection, and an Autory-shaped complex acceptance fixture are implemented.

  1. Add named output definitions that can represent installers, archives, wheels, native executables, and hook-generated artifacts.
  2. Support deterministic files and constrained glob pickup with required match counts.
  3. Resolve output dependencies through config interpolation without making hooks mutate hidden app-builder state.
  4. Publish selected output groups through GitHub and expose the resolved artifact inventory to hooks.
  5. Port an Autory-shaped test project to the new model and make it a maintained acceptance fixture.

Gate 6: reproducibility, cache, and completion semantics

Current: dependency, runtime, cache, and build-reporting work is implemented. Asynchronous post-uninstall completion remains a documented limitation.

  1. Separate lock verification from lock regeneration and enforce available artifact hashes.
  2. Pin runtime and launcher sources and record digests.
  3. Move managed versions to a writable user cache with collision-proof keys and refresh policy.
  4. Give automated uninstall a truthful synchronous completion mode while retaining a self-deleting worker where necessary.
  5. Add clear staged progress and durable diagnostic logs for long builds and cleanup workers.
The implementation work in Gates 1, 3, 4, and 5, plus most of Gate 6, has landed on this branch. Gate 2 is the principal remaining enforcement gap; signing and synchronous post-uninstall completion remain explicit release-policy and product decisions.

Final release gate

The release owner should not publish until every item below is evidenced by CI or a recorded rehearsal.

  • All Linux and Windows checks pass from a clean clone.
  • ZIP and 7-Zip reject traversal and destination collisions.
  • The actual installer EXE passes fresh install, same-version replacement, prior-1.x upgrade, rollback, and uninstall.
  • At least two representative legacy 0.x layouts upgrade and leave no stale Installed Apps or Start Menu entries.
  • Installed Apps launches the installed uninstaller and its record disappears after completion.
  • The package version, CLI version, manifest version, filenames, tag, release title, and target commit match.
  • The wheel and app-builder installer both open the same shipped help document.
  • The exact release assets, checksums, notes, and signing status are reviewed before upload.
  • A maintained Autory-shaped fixture produces and publishes every expected asset.
  • Fresh install, upgrade, and uninstall leave no audit directories, PATH entries, shortcuts, registry entries, or cleanup workers behind.
Recommended next PR Add the deliberately deferred Windows CI matrix on a separate branch. It should run the real installer EXE across ZIP and 7-Zip, replacement, rollback, legacy adoption, locked-file, hook-failure, and uninstall cases, retaining installers and logs whenever a job fails.
